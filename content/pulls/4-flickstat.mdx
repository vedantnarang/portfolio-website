## Problem

Four data providers cover world football â€” Transfermarkt, WhoScored, Understat, BSD â€”
and none of them agree on who a player *is*. Transfermarkt says `HÃ©ctor BellerÃ­n`,
WhoScored says `Hector Bellerin`, Understat says `Bellerin`, and no two share an ID.
Every analytics feature I wanted to build (xG leaders, defensive workhorses, live
World Cup coverage) dies at exactly this point: you cannot join what you cannot identify.

The constraints that shaped everything else:

- **A wrong match is worse than no match.** Attaching one player's stats to another
  silently corrupts every number downstream, and nothing on the read path can detect it.
- The pipeline runs **unattended on cron** during a live tournament â€” 3am failures
  must self-heal or wait, not page me.
- 471k event rows means aggregation belongs **in Postgres**, not in request handlers.

## Approach

Strict layering, each stage re-runnable in isolation:

**Scrapers write raw rows and never resolve identity.** Four independent provider
ingesters (Playwright / SeleniumBase in UC mode for the Cloudflare-fronted one) land
data in untouched `raw_*` tables keyed by deterministic natural keys, so any script
can be killed mid-run and re-run safely via `upsert â€¦ on_conflict`.

**An in-memory resolver owns identity.** A seven-stage matching cascade stops at the
first hit â€” exact name + DOB, seeded aliases, exact name, DOB disambiguation, token
subsets ("Bruno Fernandes" âŠ‚ "Bruno Miguel Borges Fernandes"), then fuzzy scoring
*only within hard-gated candidate spaces* (same DOB, or the resolved team's 26-man
squad â€” a ~50Ã— reduction that makes thresholds safe). Every match records *how* it was
made; a spike in `fuzzy+name` matches is an audit signal that something upstream moved.

Result across both problems: 1,277/1,320 World Cup squad slots matched (96.7%) with
**zero wrong matches**, verified by an independent DOB-audit query run after every
batch â€” deliberately separate logic from the matcher itself. That audit caught four
wrong matches the prevention layer had already let through.

Serving reads goes through ~14 `STABLE` SQL RPCs â€” e.g. defensive-workhorse
breakdowns aggregate 471k events with `COUNT(*) FILTER` clauses in one scan, exposed
via `SECURITY DEFINER` with pinned `search_path` so the RLS-locked raw tables stay
closed while one curated query stays open. Live tournament scores ride a long-lived
asyncio WebSocket relay with reconnect loops and a write gate that drops frames for
non-tournament events.

## Tradeoffs

- **Raw tables stay untouched and unnormalized.** Storage cost is real (~470k rows Ã—
  providers), but re-processing history after a resolver bug costs a scripted re-run
  instead of a 12-hour re-scrape. I'd make this trade again.
- **Identity matching lives in Python, not SQL.** `pg_trgm` could do the fuzzy part,
  but the cascade's value is its *ordering* â€” cheap exact passes first, fuzzy last,
  uniqueness gates on every fallback â€” plus per-match method labels for auditing.
  In-memory over tiny candidate spaces made round-tripping to the database pure loss.
- **`SECURITY DEFINER` is a loaded gun.** One function with a stale `search_path`
  becomes an accidental public API. It's the right call for RLS-locked analytics, but
  it demands review discipline I now apply everywhere: pin the path, keep the function
  read-only, expose nothing table-shaped.
- **Free scraping sits behind anti-bot walls.** SeleniumBase UC mode works today;
  a selector or challenge change breaks ingestion without warning. I accepted that
  operational risk rather than pay for official feeds at zero revenue.

## What I'd do differently

the impostor incident â€” verification logic designed alongside prevention would have

<Review author="reviewer" q="Idempotent upserts are claimed â€” but what happens if two runs overlap?">
They can't: GitHub Actions concurrency groups ensure one pipeline at a time, and every

write time) with `on_conflict`. The high-water marks are derived from the data itself â€” newest
row with a real player attached, not a naive MAX(date), because future fixtures get
inserted early as placeholders and would stall every later run.
</Review>
